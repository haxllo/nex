Hotfix release for the first-run freeze that hit some installs of 2.15.0. The overlay now opens the instant you press the hotkey — even while the search index is still being rebuilt in the background — and a couple of nasty WebView2 startup races are gone for good.

## User-Reported Issues

- [x] After installing 2.15.0, pressing the hotkey right after install froze the PC for ~3s and nex didn't open until restart → **fixed** (two separate bugs: show blocked on the service lock during first-run indexing; power popup's WebView2 environment raced the overlay's build and wedged the host loop)
- [x] Running the dev binary (`--foreground`) showed the window but the PC froze and nex crashed → **fixed** (a show/rebuild path destroyed and recreated the WebView2 controller while the power popup was building its own environment — same underlying race)
- [x] Restart after a freeze took ~18s with a full re-index → **fixed at the source** (the re-index was fallout of force-killing the wedged process mid-write; the wedge no longer happens)

## Changelog (1 PR since v2.15.0)

### Bug Fixes

- **Overlay opens instantly during indexing**: the show path used a blocking read on the service lock, so a hotkey pressed while the background indexer was mid-rebuild (e.g. tantivy corruption on first run) stalled the whole worker — the overlay only appeared after the index finished, and keystrokes queued up and fired late. Warm-up and quick-launch loads now use non-blocking `try_read` and retry from the event tick once the lock frees. The window appears immediately, rows stream in.
- **WebView2 environment race at startup**: the power popup built its own WebView2 environment from the runtime worker thread, racing the host thread's eager overlay webview build. WebView2 environment creation is not concurrency-safe across threads sharing a user-data folder — one build hung and the other failed (E_INVALIDARG), so the host event loop never started and every hotkey show was silently dropped. The popup now builds strictly after the overlay webview is ready, on the same thread.
- **No rebuild on show-race**: if a show beat the eager build's ready event, the host destroyed and rebuilt the controller — which again raced the popup's environment creation (that's the freeze/crash you saw with the dev binary). A not-yet-ready webview now just waits for the ready event that's already queued.
- **Installer pre-creates the helper task** (all-users installs): the elevated `NexHelperV2` scheduled task is created during setup instead of on first launch, so the first run has no surprise UAC prompt.

### Architecture

- `try_read` discipline on the runtime worker: every service-lock access in the event path is now non-blocking, so no background activity can ever freeze hotkey handling.
